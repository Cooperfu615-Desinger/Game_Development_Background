# 第一階段頁面三層校準

本章把每個本輪頁面的資訊拆成三層，避免在整理完整規格時混淆「產品已決定什麼」、「現行畫面做了什麼」以及「未來預計補什麼」。

## 三層定義

| 層級 | 定義 | 使用限制 |
|---|---|---|
| 已確認產品規則 | 已有明確產品定位、責任邊界或跨頁共通規則支持 | 可作為後續規格不可違反的 guardrail |
| 現行原型實況 | 目前 route、元件及畫面實際可見的資訊與互動 | 只能證明 mock 現況，不代表正式 API 或資料契約 |
| 目標草案／待確認 | 規格方向已知，但 API、權限、狀態、資料或流程仍未核准 | 必須補成 Draft／TBD，不能寫成既定事實 |

## 校準狀態

| 狀態 | 意義 |
|---|---|
| 大致一致 | 原型方向符合已確認邊界，仍需補正式契約 |
| 邊界注意 | 原型含 mock、暫名或可能被誤讀為正式能力的內容 |
| 原型缺口 | 現行畫面不足以呈現已確認責任，或頁面仍為 Placeholder |

> 「邊界注意」不等於原型錯誤，而是撰寫規格時必須加註限制；「大致一致」也不代表頁面已可直接開發。

## 使用方式

1. 完整頁面規格先複製「已確認產品規則」作為不可違反的邊界。
2. 以「現行原型實況」建立畫面示意與程式追溯，但所有 mock 值與互動需明確標示。
3. 將「目標草案／待確認」轉成頁面章節、API 草案或具 owner 的 TBD。
4. 若原型與已確認規則發生直接衝突，先停止該段規格升格，由產品決定修原型或修規則。
5. Deferred 頁面不建立三層校準，直到必要輸入齊備並重新排入 Active。
