# 遊戲商監控總覽頁面規格

> 版本：0.1.0
> 更新日期：2026-08-11
> 狀態：產品方向已確認；前端仍為 Placeholder blueprint，待建立獨立 mock 原型；正式 API、警戒門檻與更新頻率待確認

本文件定義 Provider Portal「監控總覽」頁面的責任範圍、五張摘要卡、查詢條件、遊戲監控列表、詳情與跨頁導向。異常事件、嚴重度、告警、自動緩解與隔離規則統一依 [`PROVIDER_RISK_CONTROL_SPEC.md`](./PROVIDER_RISK_CONTROL_SPEC.md) 執行。

## 1. 頁面定位

監控總覽回答「目前遊戲服務、遊戲回合與 GGAP 直接對接是否有問題，以及應前往哪個頁面確認」。本頁是快速判讀與分流入口，不是歷史分析報表或告警操作工作台。

第一版主要目標：

- 讓營運、技術與風控快速看出目前是否存在服務問題。
- 同時呈現遊戲商自身服務、遊戲回合結果與 GGAP 直接對接狀態，但不得混淆責任來源。
- 以五張摘要卡、遊戲監控列表與單款遊戲詳情完成由總覽到證據或處理頁的導向。
- 保持唯讀；正式處理統一由風控告警／處理頁負責。

本頁不包含：

- 歷史趨勢圖與完整近期 Risk Event 列表。
- Alert 工作佇列與隔離、解除、重送、結案等操作。
- 單筆 Game Round 完整內容。
- GGAP 與代理商之間的網路、錢包、會員驗證或平台內部監控。
- Test 環境監控。

## 2. 監控責任邊界

### 2.1 遊戲商自身

由「遊戲服務健康」與「遊戲回合成功率」呈現：

- 遊戲服務與必要內部服務是否正常。
- 遊戲是否可啟動、產生結果並完成應有的遊戲回合流程。
- 遊戲商已建立的 Provider Game Round 成功、失敗與逾時結果。
- 遊戲商自己的隔離、緊急停止與健康檢查狀態。

### 2.2 遊戲商與 GGAP 直接對接

由「GGAP 請求延遲」與相關 Risk Event 呈現：

- GGAP 傳入遊戲商的請求與遊戲商回應時間。
- 遊戲商送往 GGAP 的請求、通知或回呼與 GGAP 回應時間。
- 逾時、失敗、重試、HTTP 錯誤與 GGAP 業務錯誤。

GGAP 直接對接異常不得直接改寫成遊戲商服務異常。當遊戲本身正常但 GGAP 對接異常時，畫面應可同時呈現「遊戲服務正常」與「GGAP 對接異常」。

### 2.3 GGAP 與代理商

此範圍由 GGAP 負責。Provider Portal 不推論未抵達遊戲商的請求發生於 GGAP 或代理商哪一側，也不將代理商至 GGAP 的延遲或錯誤計入本頁摘要。

若未來 GGAP 主動提供下游狀態，只能作為「GGAP 回報」的參考脈絡，不納入遊戲服務健康數字，除非另立並核准端到端可用性規格。

## 3. 資料範圍與時間語意

| 項目 | 定義 |
|---|---|
| 頁面 Route | `/monitoring` |
| 環境 | Production 或 DEMO，單選且不可混合 |
| 預設環境 | Production |
| 不納入環境 | Test |
| 時區 | `UTC+08:00 Asia/Taipei` |
| 預設分析時間 | 目前時間往前 24 小時 |
| 快速分析時間 | 近 1 小時、近 6 小時、近 24 小時、自訂時間 |
| 自訂時間上限 | 第一版建議最多 7 日；更長區間導向風控報表 |
| 主要列表單位 | 目前環境中的一款遊戲 |

五張摘要卡包含兩種時間語意：

### 3.1 目前狀態

不受分析時間區間限制，始終顯示目前仍有效的狀態：

- 遊戲服務健康。
- 高風險告警。
- 未處理異常。

舊告警或事件即使早於目前分析區間，只要仍未結案或未完成處理，就不得被時間條件隱藏。

### 3.2 分析時間

依目前選擇的滾動或自訂區間重新計算：

- 遊戲回合成功率。
- GGAP 請求延遲。
- 遊戲監控列表內的期間統計欄位。

時間控制旁必須顯示「分析時間只影響遊戲回合成功率、GGAP 請求延遲與期間明細」，不得讓使用者誤以為五張卡都受時間限制。

## 4. 頁面結構

第一版由上到下包含：

1. 查詢條件、手動重新整理、自動更新與最後更新時間。
2. 五張監控摘要卡。
3. 關注項目分段選項。
4. 遊戲監控列表。
5. 單款遊戲監控詳情視窗。

頁面已有主要內容後，不保留 Hero、功能說明、頁面責任範圍或 Placeholder blueprint。頁面採 1500px 最大寬度，並遵循 [`PROVIDER_PORTAL_UI_LAYOUT_SPEC.md`](./PROVIDER_PORTAL_UI_LAYOUT_SPEC.md)。

## 5. 查詢條件

### 5.1 監控範圍

| 條件 | 選項與行為 | 預設值 | 影響內容 |
|---|---|---|---|
| 環境 | 正式環境（Production）、展示環境（DEMO） | 正式環境 | 全部摘要卡、列表與詳情 |
| 遊戲類型 | 全部、老虎機、單人 Crash、棋牌及正式遊戲類型 | 全部 | 全部摘要卡、列表與詳情 |
| 遊戲 | 可搜尋單款遊戲；依環境與遊戲類型提供選項 | 全部 | 全部摘要卡、列表與詳情 |

未部署至目前環境的遊戲不出現在遊戲選項。第一版不加入代理商、商戶、會員、Risk Event ID、Alert ID、Provider Game Round ID 或 GGAP Round ID；精確查詢由專屬報表負責。

### 5.2 分析時間

- 近 1 小時。
- 近 6 小時。
- 近 24 小時，預設。
- 自訂時間，包含起始與結束時間。

分析時間只影響本文件第 3.2 節所列內容。

### 5.3 關注項目

摘要卡下方使用分段選項：

- 全部。
- 服務異常。
- 遊戲回合失敗。
- GGAP 延遲／逾時。
- 高風險告警。
- 未處理異常。

關注項目只篩選遊戲監控列表，不重新計算摘要卡。點擊摘要卡會套用對應關注項目；再次點擊同一卡片會清除快捷條件並回到「全部」。

| 摘要卡 | 套用的關注項目 |
|---|---|
| 遊戲服務健康 | 服務異常 |
| 遊戲回合成功率 | 遊戲回合失敗 |
| GGAP 請求延遲 | GGAP 延遲／逾時 |
| 高風險告警 | 高風險告警 |
| 未處理異常 | 未處理異常 |

### 5.4 查詢與更新操作

- 保留「查詢」與「重置」。
- 保留手動重新整理圖示、最後更新時間與自動更新開關。
- 自動更新建議預設開啟，原型以每 30 秒的 mock 更新效果呈現；正式頻率由後端與系統負載決定。
- 查詢送出後，摘要、列表與詳情必須使用同一組已套用條件，不得混用草稿條件。

重置後回到正式環境、近 24 小時、全部遊戲類型、全部遊戲與全部關注項目。

## 6. 五張監控摘要卡

### 6.1 共通規則

- 五張卡依目前環境、遊戲類型與遊戲條件計算。
- 卡片標題旁提供資訊圖示，支援滑鼠 hover 與鍵盤 focus。
- 提示可顯示摘要與最多五筆需關注項目，但不放需要穩定點擊的複雜操作。
- 點擊整張卡片只套用下方列表快捷條件；需要跨頁時由列表或詳情提供明確入口。
- 門檻由後端或風控設定提供，前端不得寫死正式警戒值。

### 6.2 遊戲服務健康

主要數值格式：`健康且可服務遊戲數 / 應提供服務遊戲數`，例如 `42 / 45`。

分母納入：

- 目前環境已上架、已啟用且預期可供玩家使用的遊戲。
- 因風控自動隔離或異常而暫停新啟動的遊戲；不得因目前不可服務而從分母移除。

分母不納入：

- 尚未上架、正式下架或停用。
- 尚未部署至目前環境。
- 排定維護中的遊戲；維護數量另於提示顯示。
- Test 環境。

分子必須同時符合：

- 最近一次健康檢查成功且資料仍在有效時間內。
- 玩家可正常啟動遊戲。
- 核心遊戲服務沒有持續錯誤。
- 沒有會阻擋服務且仍在發生的重大風控事件。
- 沒有被隔離或緊急停止。

| 狀態 | 定義 | 計入健康數 |
|---|---|---|
| 正常 | 健康檢查與核心服務正常 | 是 |
| 降級 | 仍可遊玩，但延遲、失敗率或部分服務超過警戒值 | 否 |
| 異常 | 無法啟動、核心服務失敗或持續重大異常 | 否 |
| 隔離中 | 因風控或人工操作阻擋新遊戲啟動 | 否 |
| 無資料 | 尚未取得健康檢查，或資料已超過有效時間 | 否 |
| 維護中 | 已排定的正常維護 | 不納入分母 |

提示至少顯示正常、降級、異常、隔離中、無資料與不納入統計的維護中數量，並列出最多五款非正常遊戲、狀態、原因與最後檢查時間。

卡片顏色依最嚴重狀態決定：全部正常為正常色；只有降級或無資料為警告色；存在異常或隔離為危險色；只有維護項目不視為事故。

### 6.3 遊戲回合成功率

主要數值格式：百分比，例如 `99.8%`。輔助資訊顯示成功、失敗與逾時數。

```text
遊戲回合成功率
= 成功完成的遊戲回合數
÷（成功完成數＋失敗數＋逾時數）
× 100%
```

資料來源以遊戲商建立的 Provider Game Round 為主；不使用 GGAP 與代理商之間的下游資料。已正式建立的 Game Round 即使根因屬 GGAP 直接對接，仍保留實際成功或失敗結果，並以異常來源另外區分責任。

成功必須符合：

- 投注已由遊戲商接受。
- 遊戲結果已產生。
- 派彩或輸贏結果已完成。
- 遊戲回合進入最終完成狀態。
- 沒有仍待處理的結算錯誤。

失敗或逾時包含遊戲執行失敗、結算失敗、超過規範時間仍未完成、必要資料缺失而無法完成，以及被系統判定失敗的卡住回合。已退款或補償仍屬原始流程失敗。

不納入正常處理期限內的進行中回合、投注前即離開、前置驗證拒絕且未建立正式 Game Round、內部健康檢查，以及同一 Game Round 的重試事件。每個 Provider Game Round ID 只計算一次。

正式資料建議提供統一的 `finalized_at`；若無此欄位，後端需由 `settled_at`、`failed_at` 或逾時判定時間建立一致統計時間。

提示至少顯示成功、失敗、逾時、未納入的處理中數量與公式結果，並列出最多五款成功率最低的遊戲、失敗數與主要失敗類型。

### 6.4 GGAP 請求延遲

主要數值顯示查詢期間的整體 P95，例如 `P95 182 ms`；輔助資訊顯示逾時與失敗數。P95 只以成功取得回應的請求計算，卡片狀態仍須同時考量逾時率與失敗率。

依方向分開保留：

| 方向 | 計算方式 |
|---|---|
| GGAP → 遊戲商 | 遊戲商收到請求至送出回應的處理時間 |
| 遊戲商 → GGAP | 遊戲商送出請求至收到 GGAP 回應的往返時間 |

依正式契約分別保留遊戲啟動、遊戲回合、結算、回呼、健康檢查與其他對接類型。主卡可顯示整體 P95，但提示必須拆分方向與類型，並顯示總請求數、P50、P95、P99、逾時、失敗與重試數。

狀態包含：

- 正常：P95、逾時率與失敗率均低於各 API 門檻。
- 延遲升高：仍能完成，但 P95 或錯誤率超過警戒值。
- 異常：大量逾時、持續失敗或直接對接中斷。
- 無資料：查詢期間沒有請求；不得直接顯示正常。

提示列出最多五個最需關注的遊戲與對接類型。不同 API 的門檻不得使用單一前端常數。

### 6.5 高風險告警

主要數值為目前尚未結案、尚未標記誤報，且嚴重度為「嚴重」或「高」的不重複 `alert_id` 數量。

納入待處理、調查中，以及已緩解但尚未完成覆核或結案的 Alert。不納入已結案、誤報與 Test。此卡不受分析時間區間限制，必須標示「目前未結案告警」。

提示至少顯示：

- 嚴重與高的數量。
- 待處理、調查中與已緩解待覆核數量。
- 逾期未覆核與自動處理失敗數量。
- 最多五筆優先告警的遊戲、異常類型、嚴重度、隔離與處理狀態。

提示排序：嚴重、自動處理失敗、已逾期、高、最後更新時間由新到舊。排序需與風控告警／處理工作佇列一致。

狀態判斷：沒有高風險告警為正常；只有「高」為警告；存在「嚴重」、自動處理失敗或逾期為危險。

### 6.6 未處理異常

主要數值為目前狀態為「待處理」或「調查中」的不重複 `risk_event_id` 數量，包含所有嚴重度與尚未建立 Alert 的事件。

不納入已緩解、已關閉、誤報與 Test。此卡不受分析時間區間限制，必須標示「目前未完成事件」。

提示至少顯示：

- 待處理與調查中數量。
- 仍持續發生與尚未建立 Alert 的數量。
- 遊戲回合、遊戲服務、GGAP 請求、回呼、資料品質與遊戲數值等異常來源分布。
- 最多五筆需優先確認事件的遊戲、異常類型、嚴重度與狀態。

提示排序：嚴重、高、仍持續發生、尚未建立 Alert、最後發生時間由新到舊。

沒有未處理異常為正常；只有資訊、低或中為警告；存在高、嚴重或仍持續發生為危險。

高風險告警以 `alert_id` 計算，未處理異常以 `risk_event_id` 計算。兩張卡可能關聯同一問題，數字不得相加。

## 7. 遊戲監控列表

列表名稱使用「遊戲監控列表」，因為內容同時涵蓋服務、遊戲回合、GGAP 直接對接、Risk Event 與 Alert，不只代表健康檢查。

每列代表目前單選環境中的一款遊戲；同一款遊戲在 Production 與 DEMO 分開計算。環境已由查詢條件固定，因此主列表不重複顯示環境欄位。

### 7.1 欄位順序

| 順序 | 欄位 | 定義 |
|---:|---|---|
| 1 | 整體狀態 | 正常、降級、異常、隔離中、無資料或維護中 |
| 2 | 遊戲名稱 | 遊戲名稱與 Game ID |
| 3 | 遊戲類型 | 正式遊戲類型 |
| 4 | 遊戲版本 | 目前環境運行版本 |
| 5 | 遊戲服務 | 最近健康檢查結果 |
| 6 | 遊戲回合成功率 | 目前分析時間內成功率 |
| 7 | GGAP 請求延遲 | 目前分析時間內 P95 |
| 8 | 高風險告警 | 目前未結案的高／嚴重 Alert 數 |
| 9 | 未處理異常 | 目前待處理／調查中 Risk Event 數 |
| 10 | 最後檢查時間 | 最近健康資料更新時間 |
| 11 | 操作 | 查看監控詳情 |

成功率與延遲欄位標題旁提供公式或統計範圍提示。欄位可排序；排序作用於完整查詢結果後再分頁。

### 7.2 整體狀態

同一遊戲存在多個信號時，以最嚴重結果顯示：

1. 隔離中。
2. 異常。
3. 降級。
4. 無資料。
5. 維護中。
6. 正常。

遊戲服務正常但存在嚴重且持續發生的風控事件時，整體狀態仍可判定異常；詳情必須保留各信號原始狀態，不能只顯示合併結果。

### 7.3 預設排序

1. 隔離中。
2. 異常。
3. 降級。
4. 無資料。
5. 存在高風險告警。
6. 存在未處理異常。
7. 維護中。
8. 正常。
9. 相同條件依最後檢查時間由新到舊。

## 8. 單款遊戲監控詳情

詳情使用可容納完整內容的大型 Dialog 或獨立詳情頁，不使用狹窄側欄。至少包含：

### 8.1 遊戲與服務

- 遊戲名稱、Game ID、類型、環境與版本。
- 整體狀態、遊戲服務狀態與原因。
- 最後健康檢查時間與資料有效性。
- 是否維護、隔離或阻擋新遊戲啟動。

### 8.2 遊戲回合

- 目前分析時間。
- 成功、失敗、逾時與未納入的處理中數量。
- 遊戲回合成功率與主要失敗類型。

### 8.3 GGAP 直接對接

- 方向與 API 類型。
- P50、P95、P99。
- 逾時、失敗與重試數。
- 最近一次異常時間與錯誤摘要。

### 8.4 風控與告警

- 高風險 Alert 摘要、嚴重度、狀態、逾期、隔離與自動處理結果。
- 未處理 Risk Event 摘要、異常來源、類型、是否持續與是否已有 Alert。

### 8.5 導向入口

- 查看風控事件。
- 前往告警處理。
- 查看遊戲紀錄。
- 查看 GGAP 請求紀錄；在 GGAP 頁面規格與 route query 契約完成前，可先保留入口與原型提示。

詳情維持唯讀，不直接執行隔離、關閉遊戲、重送通知、修改 Game Round、標記誤報或結案。

## 9. 導向契約

- 風控事件導向 `/monitoring/risk-reports`，帶入完整 `risk_event_id`，並自動開啟事件詳情。
- 告警處理導向 `/monitoring/alerts`，帶入完整 `alert_id` 與對應 `risk_event_id`，並自動開啟告警詳情。
- 遊戲紀錄導向 `/reports`，帶入完整 Provider Game Round ID 或可核准的遊戲／時間查詢脈絡。
- GGAP 請求紀錄預計導向 `/ggap/requests`；正式 query 欄位待 GGAP 對接規格確認。
- 無對應 Risk Event 或 Alert 時，不顯示無效入口。
- 導向頁面仍需自行驗證 query、資料存在性與權限，不得只信任來源頁。

## 10. 載入、空資料與錯誤狀態

第一版原型必須展示：

- 初次載入與查詢中。
- 手動重新整理與自動更新中。
- 全部服務正常。
- 查無符合條件的遊戲，並保留重置入口。
- 健康資料尚未取得或已過期。
- 部分資料來源載入失敗；可保留已成功來源，不把整頁清空。
- 全部資料來源失敗，顯示重新載入入口。

部分來源失敗時，相關摘要卡與欄位顯示「無資料」或明確錯誤，不得沿用前一次數值或將無資料視為正常。

## 11. 響應式與可用性

- 桌機採 1500px 最大寬度。
- 五張摘要卡需使用穩定欄位尺寸，不因數值或提示改變造成布局位移。
- 手機版摘要卡可依序換行，查詢條件改為單欄或可讀的雙欄排列。
- 寬表格使用頁面內水平捲動，不造成整個 document 水平溢出。
- 詳情 Dialog 在手機版保留安全邊距、可垂直捲動且關閉按鈕始終可操作。
- 圖示按鈕需有 `aria-label` 與 tooltip；資訊提示需支援鍵盤 focus。
- 一般畫面使用台灣繁體中文；選項可保留中文／英文對照，ID、API、錯誤碼、HTTP 狀態碼與版本值維持原文。

## 12. 原型限制與後端待確認

前端第一版使用 mock data，重點是畫面、規格骨架、查詢影響範圍、提示、列表、詳情與導向。以下內容待後端與 GGAP 對接團隊確認：

- 健康檢查來源、頻率、資料有效期限與服務依賴。
- 各遊戲、環境、遊戲類型與 API 的降級及異常門檻。
- Provider Game Round 的成功、失敗、逾時與 `finalized_at` 正式定義。
- GGAP 雙向請求的計時點、P95 聚合方式、逾時與重試規則。
- 遊戲、Risk Event、Alert 與請求紀錄的關聯欄位。
- 自動更新 API、快取、查詢上限與部分來源失敗格式。
- GGAP 請求紀錄的正式 route query 契約。

原型不得因 mock data 方便而加入 Test、代理商管理、會員管理、GGAP 下游推論或正式處理操作。

## 13. 驗收方向

- 預設為正式環境、近 24 小時、全部遊戲類型、全部遊戲與全部關注項目。
- Production 與 DEMO 單選且資料不混合；Test 不出現。
- 五張摘要卡定義、時間語意、提示與快捷條件符合本文件。
- 目前狀態卡不受分析時間影響；期間統計卡正確套用分析時間。
- 遊戲監控列表欄位、整體狀態與排序符合本文件。
- 單款遊戲詳情同時保留服務、遊戲回合、GGAP 直接對接、Risk Event 與 Alert 的原始狀態。
- 風控事件、告警處理與遊戲紀錄導向可帶入正確識別或查詢脈絡。
- 本頁不提供任何改變營運、風控、遊戲或 GGAP 狀態的操作。
- 載入、正常、空資料、無資料、部分失敗與全部失敗狀態完整。
- 桌機與手機無整頁水平溢出，表格與 Dialog 可正常操作。
- `npm run type-check`、`npm run build` 與瀏覽器 console 驗證通過。
