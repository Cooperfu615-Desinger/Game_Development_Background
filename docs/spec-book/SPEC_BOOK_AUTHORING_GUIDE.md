# 產品規格網站撰寫與交接規範

> 文件用途：建立可供產品、設計、前端、後端與 QA 共同開發及驗收的產品規格網站。<br>
> 適用範圍：後台、平台、B2B 產品、營運系統及其他具多頁面、多角色或跨系統整合需求的專案。<br>
> 建議交付形式：Markdown 作為可維護來源、HTML 作為主要閱讀介面、PDF 作為核准版本快照。<br>
> 本文件可獨立複製至其他專案使用；最後一章才包含 Provider Portal 的專案實例。

## 1. 目標與使用方式

本規範的目的不是統一文件外觀，而是建立一套能直接支援開發的規格工作方法。完成後的規格書應讓不同角色分別回答下列問題：

| 角色 | 規格書必須能回答的問題 |
| --- | --- |
| Product／PM | 為什麼要做、服務誰、包含什麼、哪些尚未決定？ |
| UX／UI | 頁面結構、資訊優先級、狀態、響應式與互動如何運作？ |
| Frontend | Route、元件、欄位、格式、操作、狀態與 API 如何對接？ |
| Backend | 資料範圍、查詢、計算、權限、錯誤、精度及整合契約為何？ |
| QA | 如何驗證正常、邊界、錯誤、權限、資料隔離與跨系統一致性？ |
| 維運／支援 | 發生異常時使用哪些 ID、時間與狀態追蹤？ |

規格書只有在「可以定位畫面、可以實作、可以驗收、可以追溯決策」時，才算完成。單純描述畫面內容、貼上截圖或列出 API 名稱，都不足以作為正式開發規格。

## 2. 核心原則

### 2.1 單一可維護來源，多種閱讀輸出

- 使用 Markdown 或同等純文字格式作為人工維護來源，方便版本控制、審查與差異比較。
- 由來源自動產生多頁 HTML，提供目錄、搜尋、頁內跳轉、響應式與離線閱讀。
- 已核准的里程碑可輸出 PDF 快照，作為不可變的版本紀錄。
- 不直接修改產生後的 HTML；所有正式變更回到來源文件或產生器。

建議關係如下：

```text
產品決策／既有規格／程式現況
            ↓ 整理與校正
Markdown 規格來源 + 集中索引
            ↓ 自動產生
HTML 規格網站 ──→ PDF 核准快照
```

### 2.2 Overview first

使用者進入內容頁時，應先理解整體頁面，再閱讀細節。建議順序為：

1. 頁面標題、用途與規格狀態。
2. Route、前端元件等追溯資訊。
3. 可點擊的頁面畫面示意與區塊索引。
4. 重要資料邊界或閱讀提醒。
5. 詳細功能、欄位、行為與狀態規格。
6. API、權限、驗收條件及待決策事項。

畫面示意是閱讀地圖，不是裝飾。每個區塊應能連到對應詳細章節；閱讀深入後，也要提供回到畫面示意的入口。

### 2.3 畫面、資料契約與 Mock 分離

- 有畫面原型，不代表 API、權限、狀態或資料契約已確認。
- Mock 數字只用於說明排版與情境，不可被描述成正式預設值或計算結果。
- API path、enum、precision、permission key、限制門檻若未核准，必須標記 `Draft` 或 `TBD`。
- Prototype、DEMO、Test 與 Production 資料必須明確區分。
- 規格內容要描述「必須成立的規則」，而不是只抄錄目前畫面。

### 2.4 共通規則只定義一次

下列內容應集中於共通章節，頁面規格只補充例外或引用：

- 名詞與領域模型。
- 身分、角色、權限與資料範圍。
- 金額、幣別、精度與正負方向。
- 日期、時間、時區與格式。
- ID、追蹤碼與遮罩規則。
- 分頁、排序、錯誤 envelope 與 HTTP 行為。
- Loading、空資料、錯誤與權限不足的共通呈現。
- 響應式、無障礙、效能、稽核與可觀測性。

重複定義會造成頁面間口徑漂移。若頁面需要不同規則，應明確寫成例外並說明原因。

### 2.5 每個未決事項都必須可管理

不可只寫「待確認」。每個 TBD 至少包含：

- 穩定 ID。
- 待確認問題。
- 建議決策角色或 owner。
- 是否阻擋前端、後端、QA 或上線。
- 決策期限或目標版本（若已知）。

## 3. 規格書的資訊架構

大型產品不應把所有內容塞在單一文件。建議分為五層：

| 層級 | 內容 | 目的 |
| --- | --- | --- |
| 文件治理 | 版本、狀態、優先級、變更規則 | 說明規格如何被使用與核准 |
| 產品基礎 | 定位、使用者、責任邊界、資訊架構 | 建立共同上下文 |
| 功能模組 | 依導覽或領域劃分的頁面集合 | 讓讀者按工作範圍閱讀 |
| 共通規格 | API、安全、權限、非功能、QA | 避免跨頁重複與矛盾 |
| 附錄 | 資料字典、enum、route 矩陣、TBD、版本紀錄 | 集中追溯與治理資訊 |

### 3.1 建議章節樹

```text
00 文件治理與使用方式
01 產品定位與目標
02 系統與責任邊界
03 資訊架構與頁面地圖
04 共通領域規則
05 功能模組
   05.x 模組總覽
   05.x.1 內容頁 A
   05.x.2 內容頁 B
06 API 與整合契約
07 安全與權限
08 非功能性需求
09 驗收與 QA
A  資料字典
B  狀態與枚舉
C  Route 與頁面矩陣
D  待決策清單
E  版本紀錄
F  撰寫與交接規範
```

模組數量與編號可依產品調整，但「基礎、頁面、共通、附錄」四類責任不可混在一起。

## 4. 文件狀態與成熟度

### 4.1 規格成熟度

| 狀態 | 定義 | 可否直接開發 |
| --- | --- | --- |
| `confirmed`／已確認 | 產品與責任方已核准，可作為實作與驗收依據 | 是 |
| `draft`／草案 | 方向已定，仍有局部欄位或契約待核准 | 依阻擋項目判斷 |
| `outline`／待整理 | 已建立頁面、來源與責任範圍，內容尚不完整 | 否 |
| `tbd`／待決策 | 核心決策尚未形成 | 否 |

### 4.2 製作範圍必須獨立管理

規格成熟度回答「內容確認到什麼程度」，製作範圍回答「目前是否排入整理」。建議至少使用：

| 範圍 | 定義 |
| --- | --- |
| `baseline` | 已完成完整試作，作為後續頁面的撰寫與審閱標準 |
| `active` | 納入目前規格完善範圍 |
| `deferred` | 必要規格或產品決策未完成；只保留延後說明 |
| `blocked` | 已開始整理，但遇到明確且無法繞過的阻擋 |

Deferred 不等於 TBD：前者是排程狀態，後者是內容成熟度。延後頁面不應保留看似完整的空白規格骨架，只需說明原因、重新啟動所需輸入，以及目前不可作為開發依據。

### 4.3 原型成熟度必須獨立管理

可另設 `complete`、`partial`、`placeholder` 等原型狀態，但不可用它取代規格成熟度。常見組合包括：

- 畫面已完成、規格仍為 Draft：只能視為互動原型，不可推定正式 API。
- 畫面為 Placeholder、規格已 Confirmed：可開始實作，但 UI 尚未完成。
- 畫面與規格皆完成：仍需通過驗收與整合測試。

### 4.4 文件優先級

每個專案應明確定義衝突時的判斷順序。建議預設為：

1. 最新核准的產品決策與 Confirmed 規格。
2. 最新平台或跨系統整合契約。
3. 最新 API 與前後端交接文件。
4. 實際程式碼、schema 與自動化測試。
5. 歷史或封存文件。

若實際程式與核准規格不同，不可默認程式就是新規格；應先記錄差異並由責任方決定修程式或修規格。

## 5. 規格網站內容頁版型

### 5.1 頁面由上至下的固定順序

| 順序 | 區塊 | 內容 |
| ---: | --- | --- |
| 1 | 頁面標頭 | 模組、標題、用途摘要、規格狀態 |
| 2 | 追溯資訊 | 章節編號、規格狀態、Route、主要前端元件 |
| 3 | 頁面畫面示意 | 原型化結構、可點擊區塊、展開／收合 |
| 4 | 閱讀邊界 | 環境、資料範圍、金額口徑、Mock 提醒等少量標籤 |
| 5 | 詳細規格 | 目的、邊界、欄位、行為、狀態、契約與驗收 |
| 6 | 頁內目錄 | 桌機版固定於右側；窄版可隱藏或改為其他入口 |
| 7 | 前後章導覽 | 上一章、下一章與版本資訊 |

為減少無效空間，來源文件清單與原型成熟度可保留於集中索引，不必重複顯示在每個內容頁頂部。

### 5.2 寬度與閱讀密度

- 規格內文應填滿頁內目錄以外的主欄空間，不應再套用造成大面積空白的固定 `max-width`。
- 右側目錄維持可掃描的窄欄，主欄與目錄只保留明確的 grid gap。
- 表格在主欄內優先完整呈現；窄螢幕允許區域水平捲動，不應造成整頁水平溢位。
- 內容寬度增加後，段落仍應透過標題、列表、表格與說明框維持掃讀性，避免形成無分段的超長行文。

目前實作可採以下基準，再依品牌與螢幕範圍調整：

```css
.content-layout {
  display: grid;
  grid-template-columns: minmax(0, 1fr) 216px;
  gap: clamp(28px, 3.5vw, 52px);
}

.spec-content {
  width: 100%;
  max-width: none;
}
```

## 6. 頁面畫面示意規範

### 6.1 使用 HTML／CSS，而非只依賴截圖

HTML／CSS 示意適合作為主要方式，因為它可以：

- 響應不同螢幕寬度。
- 讓區塊直接連到詳細章節。
- 使用文字搜尋與輔助科技。
- 隨規格更新局部調整，不需重做整張圖片。
- 明確標示哪些是結構、哪些是 Mock。

截圖仍可用於像素級比對、歷史快照或無法快速重建的複雜畫面，但不應是唯一規格來源。WebView 或 iframe 可用於內部展示，卻容易受到環境、權限、版本與 runtime 影響，不適合作為長期、離線且可版本控制的主要規格內容。

### 6.2 擬真原則

- 參照實際原型的元件類型、資訊密度、卡片、表格、抽屜與狀態，不只複製色票。
- 規格網站可沿用產品的設計語言，但必須保留文件介面的辨識，例如狀態、章節與導覽。
- 示意圖中的固定資料要能看出欄位用途，但不可暗示為正式回應值。
- 不強制每一頁使用固定六區塊；區塊數量應由實際頁面解剖決定。
- 圖上區塊編號、快速索引與對應章節必須一致。
- 避免在 Overview 與示意圖內重複顯示相同標題或大面積圖說，將空間留給實際畫面。

### 6.3 互動與響應式

- Desktop：完整畫面示意預設展開。
- Mobile：先顯示簡潔區塊索引，完整畫面示意預設收合。
- 每個示意區塊使用一般 anchor 連結至詳細章節。
- 目標章節短暫高亮，協助使用者確認跳轉位置。
- 離開示意區後顯示「回到畫面示意」入口。
- 列印時強制展開完整示意，隱藏展開按鈕與浮動控制。

### 6.4 標註色

標註色是規格文件的閱讀輔助，不是產品狀態色。建議集中成設計 token，避免每頁自行定義。目前通用示例：

```css
:root {
  --annotation: #478eff;
  --annotation-ink: #ffffff;
}
```

若移植至其他品牌，可替換 token，但必須維持對比度與全站一致性。

## 7. 單一頁面規格的內容模型

不是每頁都需要相同章節數量。下表區分必備與條件式內容：

| 章節 | 要求 | 使用時機 |
| --- | --- | --- |
| 章節狀態 | 必備 | 所有頁面 |
| 目的與使用情境 | 必備 | 說明使用者任務與業務價值 |
| 範圍與責任邊界 | 必備 | 列出包含、不包含、資料可見性 |
| 名詞與計算口徑 | 必備或引用 | 頁面有領域名詞、金額或公式時 |
| 資訊架構與頁面區塊 | 必備 | 定義畫面順序與區塊責任 |
| 查詢條件 | 條件式 | 列表、報表、搜尋頁 |
| 列表／卡片／圖表規格 | 條件式 | 有集合式資料呈現時 |
| 摘要與彙總 | 條件式 | 有統計卡、合計或趨勢時 |
| 單筆明細 | 條件式 | 有抽屜、Dialog 或詳情頁時 |
| 狀態模型 | 條件式 | 有生命週期、工作流或 enum 時 |
| 匯出規格 | 條件式 | 有 CSV、Excel、PDF 或非同步匯出時 |
| API 契約 | 必備或引用 | 頁面需要後端資料時 |
| 頁面狀態與錯誤處理 | 必備 | 至少含 Loading、Empty、Error、Forbidden |
| 響應式與可存取性 | 必備 | 說明 Desktop、Mobile 與鍵盤行為 |
| 前端實作要求 | 必備 | state、URL、格式化、競態與元件責任 |
| 後端實作要求 | 必備 | scope、驗證、精度、效能與 audit |
| 整合與資料一致性 | 條件式 | 跨服務、跨頁或跨系統時 |
| 驗收條件 | 必備 | 必須可轉換成測試案例 |
| 測試情境清單 | 必備 | 正常、邊界、錯誤、權限與響應式 |
| 待確認事項 | 必備 | 沒有 TBD 時也應明確寫「無」 |
| 規格完成條件 | 必備 | 說明何時可升為 Confirmed |

## 8. 各類規格的寫法

### 8.1 欄位定義

每個表單、列表或明細欄位至少說明：

| 項目 | 說明 |
| --- | --- |
| 介面名稱 | 使用者看到的台灣繁體中文名稱 |
| 技術欄位 | API、query 或 view model 的穩定 key |
| 型別 | string、decimal、enum、datetime 等 |
| 必填 | Request 與 UI 是否必填 |
| 預設 | 無預設時明確寫「空」或「全部」 |
| 格式 | 小數位、千分位、時區、遮罩、截斷等 |
| 行為 | 排序、複製、跳轉、編輯、禁用條件 |
| 邊界 | null、0、負數、超長、非法值的處理 |
| 權限 | 顯示、操作、匯出及敏感資料限制 |

`null`、空字串、數值 `0` 與未授權不可使用相同顯示方式。這四種情況代表不同資料語意。

### 8.2 查詢、排序與分頁

- 區分「表單編輯狀態」與「已套用查詢狀態」。
- 指定預設條件、最大範圍、驗證規則與重設行為。
- 能重建的查詢條件應反映於 URL；敏感資料不可放入 URL。
- 說明排序由前端或後端執行，不可默認只排序當頁。
- 明確選擇 offset 或 cursor pagination；尚未決定時列為阻擋 API 的 TBD。
- 切換條件、排序、頁面大小後的頁碼行為必須明確。

### 8.3 金額、比率與計算

- 說明主要計價單位、顯示單位與換算值的優先級。
- 定義正負方向是使用者、商戶、平台或供應方視角。
- 正式金額不得使用 binary floating point 運算或傳輸。
- 定義 precision、rounding、匯率方向、來源與歷史重現方式。
- 不同幣別不可直接加總，除非規格明確定義換算基準。
- Mock 合計與正式財務公式必須分開標示。

### 8.4 日期與時間

- API 使用 ISO 8601 並包含 offset，或另有明確 timezone metadata。
- 說明查詢時間類型，例如建立時間、發生時間、結算時間。
- 定義顯示時區、日界線、跨日與夏令時間策略。
- 「最後更新時間」必須說明代表查詢完成、資料產生或來源同步時間。

### 8.5 狀態與錯誤

- enum 使用穩定技術值；主介面顯示在地化文案。
- 狀態需定義語意、可否操作、可否轉換與終態。
- Loading、Empty、Error、Forbidden、Partial data 不可混為同一狀態。
- 錯誤至少包含穩定 code、可顯示訊息或 message key、trace ID，以及必要的欄位錯誤。
- 前端隱藏按鈕不是權限控制；後端必須重新驗證 scope 與 action。

### 8.6 匯出

- 說明匯出套用哪些查詢、排序與權限。
- 說明匯出當頁或完整命中結果。
- 定義格式、編碼、欄位、檔名、上限與公式注入防護。
- 大量匯出需定義非同步任務、狀態、下載期限與通知方式。
- 匯出與畫面必須採相同資料範圍與計算口徑。

### 8.7 API 契約

API 草案至少包含：

- HTTP method 與 path。
- path、query、header 與 body 欄位。
- Request／response example。
- Pagination、sorting、filtering。
- Amount、datetime、enum 的傳輸格式。
- Error envelope 與 HTTP status。
- 權限與資料 scope。
- Idempotency、retry、timeout 與 audit（適用時）。

尚未核准的 API 必須在章節開頭明示「Draft，不是正式契約」。

## 9. 驗收條件與完成定義

### 9.1 驗收條件的分類

至少拆成：

1. 功能驗收：使用者任務、欄位、查詢、操作與狀態。
2. 權限與隔離：跨租戶、跨角色、直接修改 URL 或 ID。
3. 資料品質：精度、null、0、負數、時區、enum 與跨頁一致性。
4. 體驗與可存取性：鍵盤、焦點、螢幕閱讀器、非色彩辨識。
5. 技術與非功能：競態、效能、逾時、追蹤碼與正式資料量。
6. 整合驗收：跨服務識別碼、重送、冪等與狀態同步。

### 9.2 好的驗收條件

好的驗收條件必須：

- 可觀察，不使用「正常」、「適當」、「友善」等無法驗證的形容詞。
- 包含前置條件、操作、預期結果與必要資料範圍。
- 能區分正常、邊界、錯誤、權限與響應式情境。
- 不依賴 Mock 的固定筆數或固定日期。

### 9.3 規格完成定義

內容頁可升為 Confirmed 的最低條件：

- 目的、範圍與責任邊界已核准。
- 阻擋開發的 TBD 已有決議。
- 欄位、狀態、金額、時間與權限口徑一致。
- 正式 API schema、enum 與錯誤契約已審查。
- Desktop、Mobile、Loading、Empty、Error、Forbidden 已定義。
- 前端、後端與 QA 都能從文件形成各自工作項目。
- 規格、原型、route 與程式對應已完成一次校正。

## 10. 文字、格式與命名規則

### 10.1 語言

- 主介面與規格敘述使用目標市場的主要語言；台灣產品使用台灣繁體中文。
- 英文保留於技術值、ID、protocol、method、enum、path、欄位名稱與必要選項輔助。
- 同一名詞固定使用同一翻譯，不在不同頁面混用近義詞。
- 技術值使用反引號，例如 `provider_round_id`、`GET /api/v1/items`。

### 10.2 敘述方式

- 使用「必須／不得」表達正式要求。
- 使用「建議」表達非強制方向。
- 使用 `Draft` 表達已有方向但尚未核准。
- 使用 `TBD` 表達尚待決策，並建立追蹤項目。
- 每條規則只表達一件事，避免將多個條件藏在長句中。
- 表格適合欄位與映射；列表適合規則；流程或狀態圖適合多步驟關係。

### 10.3 標題與 anchor

- 標題使用穩定編號與名稱，避免頻繁改名造成外部連結失效。
- 畫面區塊連結必須指向真實存在的 anchor。
- 技術文件避免在標題使用過多符號，以免不同 Markdown renderer 產生不同 slug。

## 11. 響應式、可存取性與列印

### 11.1 Desktop

- 顯示左側全站導覽、主內容與右側頁內目錄。
- 頁面示意完整展開，主內容填滿可用欄寬。
- 頁內目錄可 sticky，但不可遮蔽頁尾或重要操作。

### 11.2 Mobile

- 左側導覽改為抽屜。
- 右側頁內目錄隱藏或改為頁首入口。
- 頁面示意預設收合，快速區塊索引保持可用。
- 表格使用區域水平捲動或另有不遺失必要欄位的卡片方案。
- 不允許整頁水平溢位。

### 11.3 可存取性

- 使用語意化 landmark、heading、table、nav、figure 與 button。
- 所有互動支援鍵盤並具明確 focus 樣式。
- 展開控制同步 `aria-expanded` 與 `aria-controls`。
- 狀態、正負與嚴重度不可只依賴顏色。
- 目標跳轉保留足夠 scroll offset，避免被固定頁首遮住。
- 遵守 `prefers-reduced-motion`。

### 11.4 列印與離線

- 使用相對資源路徑，確保產生後的 HTML 可離線閱讀。
- Print CSS 隱藏導覽、搜尋、浮動按鈕與非必要控制。
- 列印時展開被收合的正式內容。
- 表格避免被任意裁切；必要時調整字級或分頁策略。

## 12. 維護流程

### 12.1 新增或整理一個頁面

1. 確認產品定位、責任邊界與現行來源。
2. 核對目前 route、導覽、前端元件與實際畫面。
3. 在集中索引建立頁面 ID、模組、狀態與來源。
4. 先寫目的、包含、不包含與資料可見性。
5. 建立頁面區塊與 Overview 畫面示意。
6. 按功能補齊欄位、行為、狀態與條件式章節。
7. 整理 API、權限、前後端責任與資料一致性。
8. 將未決問題轉為具 owner 與阻擋範圍的 TBD。
9. 撰寫可轉換成測試案例的驗收條件。
10. 產生 HTML，執行結構、連結、響應式與 build 驗證。

### 12.2 正式決策變更

1. 先更新規格來源與版本紀錄。
2. 更新集中索引中的狀態、來源或 route。
3. 同步原型、API schema、程式與測試。
4. 執行自動檢查與人工畫面 QA。
5. 若為核准里程碑，輸出 PDF 或版本化靜態快照。

### 12.3 不再適用的內容

- 不直接刪除仍有追溯價值的舊決策。
- 將失效文件移至 archive，標明取代版本與原因。
- 歷史文件不得繼續出現在現行導覽或被引用為正式規格。

## 13. 自動化與品質檢查

規格網站至少應自動檢查：

- 文件 ID 不重複。
- 所有索引頁與內容頁成功產生。
- 本機 HTML 連結與 anchor 存在。
- 語系、main landmark、目前導覽狀態存在。
- 來源標記未洩漏至產生結果。
- Overview 出現在詳細內文之前。
- 畫面示意的區塊數與快速索引一致。
- Print CSS、響應式樣式與必要資源存在。
- 產生結果不依賴絕對本機路徑。

人工 QA 至少包含：

- 一個主要 Desktop 尺寸。
- 一個寬螢幕尺寸，確認主欄沒有被不必要的最大寬度限制。
- 390px Mobile。
- 區塊跳轉、目標高亮、展開／收合與返回示意圖。
- 表格、長 ID、長標題與程式碼的溢位。
- Browser console error／warning。
- 列印預覽或 PDF（核准版本）。

若規格網站與應用程式共用 repository，建議在 `dev` 與 `build` 前自動重新產生規格網站，避免閱讀到過期輸出。

## 16. 常見反模式

- 只有截圖，沒有欄位、狀態、行為與資料規則。
- 只有 UI 規格，沒有權限、錯誤、精度與後端責任。
- 把目前 Mock 的數字當成正式預設或驗收值。
- 用「同設計稿」、「正常處理」、「依後端回傳」取代明確契約。
- 每頁各自定義時間、金額、enum 或錯誤格式。
- 把 Placeholder 當成已完成規格，或把完整原型當成已確認 API。
- 把 TBD 留在段落中，沒有 ID、owner 與阻擋範圍。
- 直接修改產生後 HTML，導致下次 build 被覆蓋。
- 規格內文再套固定最大寬度，寬螢幕留下大量無效空間。
- 畫面示意與 Overview 重複顯示大標題和說明，推遲實際內容出現。
- 桌機畫面成立，但 Mobile、列印或離線閱讀失效。
- 規格更新後未核對 route、元件、schema 與測試。

## 18. 移植至其他專案

最小移植步驟：

1. 複製本文件作為新專案的規格治理基準。
2. 建立集中索引，先列出模組、頁面、route、元件、成熟度與製作範圍。
3. 建立文件治理、產品定位、責任邊界、共通規則與 TBD 清單。
4. 選擇最複雜且具代表性的頁面作為 pilot。
5. 完成 pilot 的 Overview、完整頁面規格、API 草案與驗收條件。
6. 由產品、前端、後端與 QA 共同審查模板。
7. 定版後再批次整理其他頁面，避免一開始大量複製未確認結構。
8. 將規格 build 與檢查納入專案既有 CI 或 release 流程。

移植時應替換：品牌、顏色 token、產品責任邊界、狀態名稱、目錄結構、技術棧與 build 指令。應保留：Overview-first、狀態分離、共通規則、可追溯 TBD、可驗收內容與自動產生流程。

### 19.4 專案特有規則

- Provider 不建立錢包，也不管理代理商、商戶或會員主資料。
- Game Round 是主要業務紀錄單位，不另建 Game Session。
- Production 財務與遊戲紀錄不得混入 DEMO 或 Test 資料。
- Test 不納入 Provider 風控監控。
- 金額以 Provider 點數為主，USDT 為換算對照。
- GGAP 對已上架遊戲控制各代理商是否開放。

上述領域規則屬 Provider Portal，不是本規範的通用要求；移植至其他產品時必須改成該產品自己的責任邊界與資料規則。

## 20. 最終原則

規格網站的價值不在於文件看起來完整，而在於它能持續降低溝通與返工成本。任何新增內容都應通過三個問題：

1. 這項內容是否讓讀者更快理解整體與責任邊界？
2. 這項內容是否足以讓前後端做出一致實作？
3. 這項內容是否能轉換成明確驗收與追蹤依據？

若三者皆否，應刪除、合併或移至歷史附錄，把有效閱讀空間留給真正影響產品行為的規則。
